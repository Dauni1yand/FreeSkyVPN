# Развёртывание на головном сервере

Порядок: поднять стек → создать администратора → войти в админку → подключить
ноду → прогнать smoke-тест.

## 0. Что нужно

- Сервер с Docker и Docker Compose.
- Домен, направленный на этот сервер, и HTTPS перед ним (см. шаг 6).
  Админка принимает пароль — по чистому HTTP его перехватят.
- Хотя бы одна заграничная нода: чистый Ubuntu/Debian, доступ по SSH с
  паролем (пароль вы введёте один раз, дальше он сменится сам).

## 1. Доступ к репозиторию

Если репозиторий приватный — не делайте его публичным «на минутку»: боты
непрерывно сканируют GitHub именно в расчёте на такие окна, и снятая копия
останется у них после того, как вы вернёте приватность. Вместо этого дайте
серверу отдельный ключ только на чтение.

На сервере:

```bash
ssh-keygen -t ed25519 -C "freeskyvpn-server" -f ~/.ssh/freeskyvpn -N ""
cat ~/.ssh/freeskyvpn.pub
```

Вывод последней команды скопируйте в GitHub: репозиторий → **Settings** →
слева **Deploy keys** → **Add deploy key**. Заголовок любой, ключ вставить
целиком. Галочку **Allow write access оставьте снятой** — серверу нужно
только читать, а ключ на сервере украсть проще, чем на вашей машине.

Чтобы не подставлять ключ в каждую команду, пропишите его в SSH-конфиг:

```bash
cat >> ~/.ssh/config <<'EOF'
Host github-freeskyvpn
    HostName github.com
    User git
    IdentityFile ~/.ssh/freeskyvpn
    IdentitiesOnly yes
EOF
chmod 600 ~/.ssh/config
```

`IdentitiesOnly yes` здесь не для красоты: без него ssh сначала переберёт все
остальные ключи, а GitHub разорвёт соединение после нескольких неудачных
попыток — и вы получите «Permission denied» при полностью верном ключе.

Проверка и клонирование:

```bash
ssh -T git@github-freeskyvpn      # ждём "Hi <owner>/<repo>! You've successfully authenticated"
git clone github-freeskyvpn:<владелец>/<репозиторий>.git freeskyvpn
cd freeskyvpn
```

Дальше обновляться — обычный `git pull`, ключ подставится сам.

Deploy key привязан к одному репозиторию: тот же ключ во второй репозиторий
GitHub не примет, для него нужно генерировать новый.

## 2. Конфигурация

```bash
cp .env.example .env
```

Сгенерируйте три ключа и впишите их в `.env`. Делается на хосте, а не через
compose: стек намеренно отказывается стартовать с пустыми ключами, так что
через него их не получить.

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(48))"   # HEAD_SECRET_KEY
python3 -c "import secrets; print(secrets.token_urlsafe(48))"   # SECRETS_KEY
python3 -c "import secrets; print(secrets.token_urlsafe(48))"   # ADMIN_API_TOKEN
```

Если Python на хосте нет: `openssl rand -base64 36`.

- `HEAD_SECRET_KEY` — подписывает сессии админки и служит токеном приложения
  (заголовок `X-Service-Token`). Меняете — все разлогинятся, а приложению
  нужна новая сборка.
- `ADMIN_API_TOKEN` — токен служебных вызовов бота и нод (заголовок
  `X-Admin-Token`). **В приложение он не попадает никогда.**
- `SECRETS_KEY` — шифрует SSH-учётки нод в базе. **Потеряете — доступ к нодам
  из админки не восстановить** (придётся заходить на ноды вручную).
  Сохраните все три строки отдельно от сервера.

### Почему токена два

`HEAD_SECRET_KEY` вкомпилирован в APK, который лежит в открытом доступе.
Достать его оттуда — вопрос десяти минут, так что считайте его известным
всем. Он открывает ровно то, что и так делает приложение: регистрацию
устройства, выдачу конфига, учёт рекламы.

Всё, что дороже, — выдача доступа руками, подтверждение просмотра рекламы,
регистрация ноды, одобрение обновления Xray — закрыто вторым токеном,
которого в приложении нет. Его знают только голова, бот и ноды.

Разделение проверяется тестом `head/tests/test_api_token_split.py`: он берёт
живую схему OpenAPI и падает, если новый служебный маршрут окажется открыт
токеном приложения. Добавите роутер — тест напомнит, каким ключом его
закрывать.

Заполните `POSTGRES_PASSWORD` и `TELEGRAM_BOT_TOKEN` (от @BotFather).

## 3. Сертификат головы

Каждая нода настраивается доверять **ровно этому** сертификату. Потеряете —
ноды придётся переустанавливать.

```bash
mkdir -p secrets && ./provisioning/generate_head_client_cert.sh secrets/
chmod 600 secrets/head_client_key.pem
```

## 4. Запуск

```bash
docker compose up -d --build
docker compose logs -f head     # дождитесь "Application startup complete"
```

Миграции применяются при старте головы автоматически.

## 5. Администратор

```bash
docker compose exec head python -m app.cli create-admin admin
```

Пароль будет напечатан один раз — сохраните. Повторный запуск той же команды
сбрасывает пароль, это же и способ восстановления доступа.

## 6. HTTPS

Голова слушает `127.0.0.1:8000` и наружу не торчит намеренно. Поставьте перед
ней Caddy или nginx с сертификатом. Пример для Caddy (`/etc/caddy/Caddyfile`):

```
admin.вашдомен.ru {
    reverse_proxy 127.0.0.1:8000
}
```

Оставьте `ADMIN_COOKIE_SECURE=true` — тогда cookie сессии не уйдёт по HTTP.

## 7. Подключение ноды

Двумя способами, оба делают ровно одно и то же — вызывают `provision_node`.

### Из консоли

Ничего, кроме SSH к голове, не нужно:

```bash
docker compose exec head python -m app.cli add-node \
    <ip ноды> <страна> '<пароль root от хостера>'
```

Необязательные ключи: `--ssh-user`, `--ssh-port`, `--uplink-mbit`,
`--capacity`, `--control-sni`. Посмотреть, что уже подключено:

```bash
docker compose exec head python -m app.cli list-nodes
```

Если `add-node` упал на связи — сначала выясните, с какой она стороны:

```bash
docker compose exec head python -m app.cli check-node <ip ноды>
```

Три возможных ответа, и лечатся они по-разному:

- **«порт открыт, за ним ssh»** — сеть в порядке, дело было в другом
  (пароль, запрет входа root по паролю);
- **«соединение отклонено»** — хост жив, но на этом порту никого нет:
  либо sshd на другом порту (`--ssh-port`), либо не запущен;
- **«пакеты отбрасываются молча»** — до sshd дело не дошло. Фаервол
  хостера ноды (проверяется в его панели, а не на самой ноде), другой порт,
  или закрыт исходящий 22 у самой головы. Последнее отделяется так:

  ```bash
  docker compose exec head python -m app.cli check-node github.com
  ```

  Отвечает — исходящий 22 у головы открыт, значит дело в ноде. Тоже
  молчит — закрыт у головы, и ни одна нода не подключится, пока хостер
  головы это не откроет.

Когда основной порт молчит, `check-node` не останавливается на «нет»: он
сам обходит порты, на которые хостеры обычно переносят ssh (2222, 22222,
2200, 2022, 222), и печатает внешний адрес головы — тот самый, который
нужно разрешить в фаерволе ноды. Отключается флагом `--no-scan`.

Отдельно стоит знать про геоблокировку: часть заграничных хостеров режет
российские диапазоны целиком. Симптом характерный — с домашнего компьютера
`ssh root@<нода>` заходит, а с головы нет.

### Или через админку

Требует браузера, то есть SSH-туннеля (§5) — на сервере, который настраивают
по SSH, это лишний крюк. Telegram для этого **не нужен**: вход в админку по
паролю, бот тут ни при чём.

Админка → **Ноды** → форма:

| Поле | Что вписать |
|---|---|
| IP или хост | адрес ноды |
| Страна | метка для вас, пользователям не видна |
| Канал ноды | Мбит/с — при загрузке полоса уходит первыми тем, кто посмотрел рекламу |
| Ёмкость | сколько пользователей нода держит |
| SSH-пользователь / порт / пароль | доступ от хостера |

Занимает 1–3 минуты. Что происходит:

1. проверка SSH-доступа;
2. на ноду ставится сгенерированный ключ головы;
3. загружается сертификат головы, запускается bootstrap (Docker, Xray,
   marzban-node);
4. настраивается `tc`: два класса приоритета по наборам портов, которые
   передаёт голова (чтобы правила на ноде и выдаваемые порты не разошлись);
5. нода сообщает свой TLS-сертификат, голова его пиннит;
6. **пароль меняется на случайный** — тот, что вы ввели, перестаёт работать.

Дальше SSH не используется: управление идёт по REST, а при блокировке — через
Reality-туннель.

**Ноды общие.** Каждая обслуживает всех. `tc` различает два класса по порту:
`full` — те, кто оплатил час просмотром рекламы, `grace` — те, кому рекламу
показать не удалось. При загруженном канале полоса уходит первыми к `full`,
при простое любой класс разгоняется до полного канала. Разделять ноды не
нужно — достаточно одной, чтобы начать.

Ёмкость — вторая ступень приоритета: `grace` перестаёт приниматься на 80% от
неё, остаток держится для тех, кто посмотрел ролик. Когда на дашборде
загрузка подходит к этой отметке, пора добавлять ноду.

## 7а. Как устроен доступ

Платной подписки нет. При нажатии «включить» пользователь выбирает, на
сколько: **15 минут** (один пропускаемый ролик), **1 час** (один полный),
**2 часа** (два полных). Время складывается, потолок — сутки.

Кончилось время — **VPN выключается**, и включить снова можно только выбрав
пакет и посмотрев рекламу. Не кончилось, а пользователь сам выключил —
включает обратно без рекламы: эти минуты уже оплачены.

Что стоит знать до запуска:

- **Реклама не показывается — доступ всё равно выдаётся, коротко.**
  Заполнение не бывает стопроцентным, а если считать «нет ролика» за «нет
  сервиса», авария рекламной сети становится полной аварией VPN. Запасная
  выдача идёт в класс `grace` (ниже приоритетом) и ограничена по частоте,
  чтобы не стать способом пропускать рекламу. Выключается наглухо:
  `ACCESS_GRACE_MINUTES=0`.
- **Пока рекламная сеть не подключена, весь флот живёт на этом резерве.**
  Это видно на дашборде: «Реклама за сутки» покажет ноль показов и все
  выдачи запасными. Так и должно быть у сборки без SDK.
- **Голова верит клиенту на слово.** Одноразовый токен мешает записать один
  HTTP-вызов и выдавать себе доступ бесконечно, но изменённое приложение
  всё равно может запросить токен и объявить ролик просмотренным. Настоящая
  защита — серверная проверка со стороны рекламной сети: эндпоинт
  `/api/v1/ad/verify` и переключатель `AD_SSV_REQUIRED=true`, после которого
  слово клиента не принимается вообще. Включайте, как только настроите
  callback у сети.
- **Бот служебный и закрыт целиком.** Пользователи работают через
  приложение. Всё, что приходит в бота не от `TELEGRAM_ADMIN_CHAT_ID` и не
  из `TELEGRAM_ALLOWED_CHAT_IDS`, отсекается на входе — не в каждом
  обработчике, а одним middleware, чтобы новый обработчик был закрыт по
  умолчанию. Пустой список = не отвечает никому; это правильная сторона
  ошибки. Выдача доступа через бота записывается в журнал с пометкой
  источника: она обходит рекламу.
- **Ручная выдача есть в админке**, раздел «Пользователи» — в часах. Тоже
  записывается: разрыв между просмотрами и выданными часами должен быть
  объясним.
- **Отключение по истечении делает голова, а не приложение.** Раз в минуту
  просроченные пользователи убираются из Xray-конфига своих нод — это
  единственное, что реально обрывает туннель. Приложение тоже гасит VPN по
  нулю, но это вежливость: изменённая сборка так делать не станет.
  Интервал — `ACCESS_EXPIRY_INTERVAL_SECONDS`, по умолчанию 60: разрыв
  между «время вышло» и «туннель встал» — это отданный даром сервис.

Сходится ли это с расходами на серверы — считается в `economics/`:

```bash
python3 economics/ad_model.py --users 25000 --ecpm 90
```

## 7б. Домен и приложение

Адрес головы компилируется в APK. Из этого следуют две вещи.

**Заложите запасной домен сразу.** `headApiUrl` в сборке принимает список
через запятую; клиент идёт по нему, пока кто-то не ответит. Потерять IP не
страшно — A-запись переезжает, устройства не заметят. Потерять домен
страшно: все установленные копии умирают до обновления. Второй домен,
направленный на тот же сервер, ничего не стоит, пока не понадобится.

**Не все домены в `.ru`.** Российская зона быстрее и выглядит естественно,
но её делегирование снимается по решению уполномоченных органов — рычага,
которого для `.com` не существует. Основной в `.ru`, минимум один запасной в
иностранной зоне, **у другого регистратора и на другом DNS**: три домена у
одного регистратора в одной зоне — одна точка отказа в трёх лицах.

Важно и то, что домены головы приложение маршрутизирует **через туннель**, а
не мимо: иначе `api.домен.ru` попал бы под правило `domain:ru` раздельного
туннелирования, ушёл бы напрямую, и заблокированное у провайдера имя
осталось бы недоступным даже при включённом VPN. С этим правилом уже
поднятый туннель чинит проблему сам — но только если пользователь успел
подключиться.

**Для тестов домен можно не ждать.** В debug-сборке есть поле
«Настройки → Сервер»: адрес меняется на ходу. Плюс `local.properties`
правится и пересобирается за секунды.

Если домена пока нет вообще, а HTTPS нужен, работает приём с wildcard-DNS:
`157.22.252.93.sslip.io` резолвится в этот IP, и Let's Encrypt на такое имя
сертификат выдаёт. Оговорка: у `sslip.io` общий на всех лимит выпуска, так
что для боя это не замена своему домену — только чтобы начать.

## 8. SNI-пул

Админка → **SNI-пул** → «Обновить пул из источника», затем «Проверить с
&lt;ноды&gt;». Проверка идёт с ноды, а не с головы: Reality ретранслирует
хендшейк с ноды на этот домен.

Если источник популярности недоступен с вашего сервера, задайте
`SNI_SEED_DOMAINS` в `.env` или добавьте домены вручную на той же странице.

## 9. Обновления Xray

Голова сама раз в 12 часов сверяет версию Xray на каждой ноде с последним
релизом Xray-core и **ничего не ставит без подтверждения**. Причина простая:
обновление пересоздаёт контейнер на ноде, все живые подключения на ней
рвутся, и выбирать момент должен человек.

Когда обновление найдено, бот пишет в чат из `TELEGRAM_ADMIN_CHAT_ID`:
версия, список нод, кнопки «Обновить» и «Не сейчас». То же самое — в админке,
раздел **Обновления**, там же кнопка «Проверить сейчас» и история.

Подтверждённые обновления ставятся **по одной ноде за раз**, чтобы не уронить
весь флот разом. О результате бот сообщает в тот же чат.

Кнопку в Telegram видит любой, кому переслали сообщение, поэтому решение
принимается только от чата из `TELEGRAM_ADMIN_CHAT_ID` — остальным приходит
отказ.

Полезно знать:

- Xray на ноде приезжает внутри образа `marzban-node`, а не напрямую из
  XTLS. Образ может отставать от релиза на несколько дней — тогда
  обновление отработает штатно, но версия останется прежней. Это не ошибка;
  в отчёте будет приписка, а повторно голова спросит через сутки.
- Если GitHub с головного сервера недоступен, проверка молча пропускается
  (в админке это видно как «список релизов недоступен»). Ноды продолжают
  работать.
- Отклонённую версию голова больше не предлагает. Передумали — раздел
  «Обновления» в админке.
- Ноды, подключённые до появления этой возможности, обновить нельзя: на них
  нет `/usr/local/sbin/freeskyvpn-start-node.sh`. Такую ноду нужно завести
  заново через админку.

## 10. Проверка

Запускается внутри контейнера головы — там уже есть всё нужное, ставить на
сервер ничего не надо:

```bash
docker compose exec head python smoke_test.py \
    --token "$(grep ^HEAD_SECRET_KEY .env | cut -d= -f2-)" \
    --admin-token "$(grep ^ADMIN_API_TOKEN .env | cut -d= -f2-)" \
    --admin-user admin --admin-password '<пароль>'
```

Проверяет, что голова отвечает, токены совпадают с ботом, API закрыт от
неаутентифицированных, токен приложения не открывает ни одного служебного
маршрута, регистрация и выдача конфига работают, а все страницы админки
рендерятся. Возвращает ненулевой код при провале — годится для cron.

### Полная проверка

Флаг `--deep` добавляет то, чего не покажет ни один из проверок выше:

```bash
docker compose exec head python smoke_test.py --deep \
    --token "$(grep ^HEAD_SECRET_KEY .env | cut -d= -f2-)" \
    --admin-token "$(grep ^ADMIN_API_TOKEN .env | cut -d= -f2-)"
```

Что он делает дополнительно:

- **набирает выданный конфиг и смотрит, откуда выходит трафик.** Голова
  может раздавать ссылки, нода — считаться живой, и при этом ни один пакет
  не проходить. Единственное доказательство — увидеть, что внешний адрес
  сменился на адрес ноды;
- **прогоняет пакет «2 часа» целиком** и сверяет, что два ролика дали два
  часа, а не один и не четыре, и что после первого из двух доступ ещё не
  считается оплаченным полностью;
- **подключается второй раз, пока время не вышло** — рекламы быть не должно;
- **проверяет, доходит ли голова до Telegram** тем маршрутом, который
  настроен: напрямую или через `egress`;
- **сверяет ревизию миграций** в базе с той, которую ждёт код.

Запускать после подключения ноды: без неё половина проверок пропускается,
и это честно отмечается как «пропущено», а не как «пройдено».

Затем вручную: напишите боту `/start` → «Подключиться» → вставьте ссылку в
клиент (v2rayNG, Hiddify, streisand) и проверьте, что интернет ходит.

## 10а. Telegram заблокирован

api.telegram.org недоступен из РФ, а голова стоит именно там. Ломается сразу
двое: бот падает на первом запросе long polling, а голова не может доставить
алерт «нода не отвечает ни по одному каналу».

Проверить, ваш ли это случай:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://api.telegram.org
```

`200` — всё в порядке, этот раздел не нужен. Ошибка — нужен выход наружу.

### Через свои же ноды

Контейнер `egress` поднимает Xray-клиент, который идёт к вашей ноде тем же
VLESS+Reality, каким пользуются клиенты, и отдаёт остальным контейнерам
обычный SOCKS5. Со стороны это ещё один пользователь VPN, а не канал
управления — отдельной техники обхода не появляется.

Нужна хотя бы одна подключённая нода (§7). Настройка — две строки в `.env`:

```bash
COMPOSE_PROFILES=egress
TELEGRAM_PROXY_URL=socks5://egress:1080
```

```bash
docker compose up -d
docker compose logs egress     # «выход через <нода>, SOCKS5 на 1080»
docker compose logs bot        # «reaching Telegram through socks5://egress:1080»
```

`COMPOSE_PROFILES` в `.env` — это то, что заставляет обычный `docker compose
up -d` поднимать ещё и `egress`; без него контейнер не создаётся вовсе, и
установки, которым он не нужен, ничего не замечают.

Ссылку вписывать не нужно: прокси спрашивает конфиг у головы сам.

### Что происходит, когда ноду блокируют

Это не исключение, а основной сценарий, ради которого всё и делается.
Прокси раз в минуту проверяет, доходит ли он через туннель до
`api.telegram.org`. Три неудачи подряд — и он:

1. сообщает голове, что нода не несёт трафик, — тем же вызовом
   `report-failure`, каким это делает телефон;
2. получает в ответ конфиг **на другой ноде**, если она есть;
3. перезапускает Xray с новым конфигом.

Отдельного механизма переключения нет намеренно: голова уже умеет уводить
пользователей с мёртвого inbound, а прокси — обычный пользователь. Заодно
его отчёт идёт в тот же счётчик, по которому голова решает, что inbound
мёртв для всех: прокси — единственный клиент, которого можно спросить в
любой момент.

Пороги настраиваются: `EGRESS_PROBE_SECONDS`, `EGRESS_PROBE_FAILURES`,
`EGRESS_PROBE_URL`.

Наружу `egress` не публикует ни одного порта: открытый SOCKS-прокси в
интернете находят сканеры за считанные часы, и он становится чужим релеем.

### Любой другой прокси

`TELEGRAM_PROXY_URL` принимает `socks5://` и `http://` — подойдёт арендованный
прокси или SSH-туннель до вашего заграничного сервера:

```bash
ssh -f -N -D 0.0.0.0:1080 root@<заграничный сервер>
```

и `TELEGRAM_PROXY_URL=socks5://172.17.0.1:1080`. Проще для разовой проверки,
но переживает перезагрузку хуже, чем контейнер с `restart: always`.

### Оговорка про алерты

Переключение спасает от блокировки одной ноды, но не от того, что упадут
все сразу. Алерт «все ноды недоступны», отправленный через ноду, замолчит
ровно тогда, когда замолчит весь флот. Для бота это неважно — он и так
бесполезен без нод, — а для аварийного оповещения важно.

Лечится закреплением на независимом сервере: `EGRESS_VLESS_URL=vless://…`
в `.env`. Тогда прокси перестаёт спрашивать голову и переключаться, зато
не зависит от флота. Стоит ещё одной машины.

## 10б. Снести всё и поставить заново

Когда проще начать с чистого листа, чем разбираться. **Всё содержимое базы
теряется**: пользователи, ноды, выданные конфиги, журнал.

### 1. Убрать стек и данные

```bash
cd ~/FreeSkyVPN
docker compose --profile egress down -v --remove-orphans
```

`-v` — то, ради чего это делается: удаляет тома, включая `pgdata` со
старым паролем базы. `--profile egress` нужен, чтобы снесло и контейнер
выхода, если он поднимался.

Убедиться, что томов не осталось:

```bash
docker volume ls | grep -i freeskyvpn
```

Если строки остались — удалить поимённо: `docker volume rm <имя>`.

### 2. Убрать ключи и конфигурацию

```bash
rm -f .env .env.backup.*
rm -rf secrets/
```

`secrets/` — сертификат, которому доверяют ноды. Удалив его, вы обязаны
переустановить и ноды: старым они больше не поверят. Если ноды переставлять
не планируете, **не удаляйте эту папку** — тогда пропустите этот пункт
целиком и сохраните `SECRETS_KEY` из старого `.env`, иначе SSH-пароли нод в
базе всё равно не прочитать (а базу вы только что удалили, так что и это
неважно).

Проще на этом этапе: снести и ноды тоже, раз всё равно начинаете заново.

### 3. Освежить код и поставить

```bash
git pull
sudo ./install.sh
```

Скрипт спросит токен бота, ваш Telegram id и домен. Telegram из РФ
недоступен — на проверке токена он это скажет и предложит продолжить;
соглашайтесь.

### 4. Нода

```bash
docker compose exec head python -m app.cli add-node \
    <ip ноды> <страна> '<пароль root>'
```

Ноду тоже стоит переустановить с нуля, если сносили `secrets/`: у хостера
пересоздайте сервер или откатите на чистый образ.

### 5. Выход к Telegram

```bash
# в .env:
#   COMPOSE_PROFILES=egress
#   TELEGRAM_PROXY_URL=socks5://egress:1080
docker compose up -d
```

### 6. Проверить

```bash
docker compose exec head python smoke_test.py --deep \
    --token "$(grep ^HEAD_SECRET_KEY .env | cut -d= -f2-)" \
    --admin-token "$(grep ^ADMIN_API_TOKEN .env | cut -d= -f2-)"
```

Приложению после этого нужен новый `headServiceToken`: `HEAD_SECRET_KEY`
сменился, старая сборка получит 401 на каждый запрос.

## 11. Обновление

Обновление — одна команда сборки, но перед ней три шага, которые пропускают
чаще всего.

**Сначала дамп.** Миграции применяются сами при старте контейнера (`alembic
upgrade head` стоит в его CMD), автоматического отката у них нет:
восстановление — это восстановление из дампа.

```bash
cd ~/freeskyvpn
docker compose exec -T db pg_dump -U freeskyvpn freeskyvpn | gzip > ~/before-update.sql.gz
```

**Потом код.**

```bash
git status      # свои правки на сервере? сначала разберитесь с ними
git pull
```

`.env` и `secrets/` в репозитории не лежат — `git pull` их не тронет.

**Проверьте, не появилось ли новых обязательных ключей.** Релиз может
добавить переменную, которой в вашем `.env` нет: так было с
`ADMIN_API_TOKEN`. Стек намеренно не поднимается наполовину, поэтому
проверить дешевле, чем ловить потом:

```bash
docker compose config >/dev/null
```

Молчание — всё на месте. Ругань вида `required variable ADMIN_API_TOKEN is
missing a value` означает, что ключа не хватает. Проще всего дописать так:

```bash
./install.sh    # на вопрос про существующий .env ответьте «оставить»
```

Существующий `.env` он сохранит и допишет только недостающее. Руками — то же
самое:

```bash
echo "ADMIN_API_TOKEN=$(python3 -c 'import secrets; print(secrets.token_urlsafe(48))')" >> .env
```

Посмотреть весь список того, что есть в примере и отсутствует у вас:

```bash
comm -23 <(grep -oE '^[A-Z_]+=' .env.example | sort -u) \
         <(grep -oE '^[A-Z_]+=' .env | sort -u)
```

Обязательны из них только помеченные `:?` в `docker-compose.yml`; у
остальных есть значения по умолчанию.

**Сборка и проверка.**

```bash
docker compose up -d --build
docker compose logs -f head     # Ctrl-C, когда появится "Application startup complete"

docker compose exec head python smoke_test.py \
    --token "$(grep ^HEAD_SECRET_KEY .env | cut -d= -f2-)" \
    --admin-token "$(grep ^ADMIN_API_TOKEN .env | cut -d= -f2-)"
```

### Что при этом происходит с пользователями

Ничего. Голова — управляющий слой: она решает, кому какой конфиг выдать, и
рассылает конфиги нодам. Трафик идёт через Xray на нодах, а их перезапуск
головы не касается — подключённые остаются подключёнными.

Пока голова недоступна, не работает только то, что требует её участия:
новое подключение, зачёт просмотренной рекламы и отключение по истечении
времени. Последнее не потеряется — истёкшие проживут лишние минуты, и sweep
догонит их, когда голова вернётся.

Ноды обновляются отдельно и своим порядком — см. §9.

### Если новая версия не поднялась

```bash
docker compose logs --tail 50 head
git log --oneline -5
git checkout <хеш предыдущего> && docker compose up -d --build
```

Откат кода не откатывает базу: применённые миграции остаются применёнными.
Если новая версия успела изменить схему так, что старая с ней не работает,
восстанавливайте базу из дампа, снятого первым шагом.

## Что делать, если

**Нода не подключается.** Сообщение об ошибке в админке содержит лог до места
падения. Частое: у хостера закрыт 22-й порт, отключён вход root по паролю
(`PermitRootLogin yes` + `PasswordAuthentication yes` в `sshd_config`), или на
ноде нет `curl`.

**Нода стала `isolated`.** Не отвечает ни напрямую, ни через туннель.
Пользователи на ней продолжают работать — не отвечает только канал
управления. Проверьте, жив ли сервер и не заблокирован ли его IP.

**Бот молчит.** `docker compose logs bot`. Две частые причины. Первая: вашего
Telegram-id нет в `TELEGRAM_ADMIN_CHAT_ID`/`TELEGRAM_ALLOWED_CHAT_IDS` — бот
служебный и отвечает только операторам, всем остальным он отвечает отказом.
Вторая: `HEAD_ADMIN_TOKEN` в боте не равен `ADMIN_API_TOKEN` головы — в
compose это одна переменная, но при ручном запуске легко разойтись.

**`docker compose up` ругается на `ADMIN_API_TOKEN` и не стартует.** `.env`
достался от версии, где этого ключа ещё не было. Так и задумано — стек не
поднимается с пустым секретом, вместо того чтобы подняться наполовину.
Лечится одним из двух: `./install.sh` (существующий `.env` он сохранит и
допишет недостающее) или строкой руками:

```bash
echo "ADMIN_API_TOKEN=$(python3 -c 'import secrets; print(secrets.token_urlsafe(48))')" >> .env
docker compose up -d
```

**Бот отвечает, но на любом действии — ошибка доступа.** Голова не приняла
`X-Admin-Token`: `HEAD_ADMIN_TOKEN` у бота разошёлся с `ADMIN_API_TOKEN`
головы. В compose это одна переменная, так что случается только при ручном
запуске. В логе головы будет `invalid admin token`.

**Голова не поднимается: `password authentication failed for user
"freeskyvpn"`.** Пароль в `.env` верный — старым остался сам том с базой.
Postgres задаёт пароль только когда инициализирует пустой каталог данных;
том, созданный прошлой установкой, помнит прежний, и перезаполнение `.env`
этого не меняет.

Если данными можно пожертвовать (на первой установке — можно):

```bash
docker compose down
docker volume rm freeskyvpn_pgdata     # имя проекта = имя каталога
sudo ./install.sh
```

Если в базе уже есть ноды и пользователи — сменить пароль внутри неё под
тот, что в `.env`:

```bash
docker compose up -d db
docker compose exec db psql -U "$(grep ^POSTGRES_USER .env | cut -d= -f2-)" \
    -c "ALTER USER \"$(grep ^POSTGRES_USER .env | cut -d= -f2-)\" WITH PASSWORD '$(grep ^POSTGRES_PASSWORD .env | cut -d= -f2-)';"
docker compose up -d
```

По локальному сокету внутри контейнера пароль не спрашивается, поэтому
команда проходит даже при разошедшихся паролях.

**Забыт пароль админки.** `docker compose exec head python -m app.cli
create-admin admin` — задаёт новый.

**`git clone` просит пароль или отвечает Permission denied.** Ключ не
подхватился. Проверьте `ssh -T git@github-freeskyvpn` — там будет причина.
Частое: забыт `IdentitiesOnly yes` (ssh перебирает чужие ключи и упирается в
лимит попыток), права на `~/.ssh/freeskyvpn` шире 600, или клонируете по
`git@github.com:` вместо `github-freeskyvpn:` — тогда конфиг не применяется.

## Резервное копирование

```bash
docker compose exec -T db pg_dump -U freeskyvpn freeskyvpn | gzip > backup.sql.gz
```

Отдельно и обязательно сохраните `secrets/` и обе строки ключей из `.env`:
без `SECRETS_KEY` дамп базы бесполезен для доступа к нодам, без
`head_client_key.pem` ноды придётся переустанавливать.
