# Архитектура FreeSkyVPN

Панель управления флотом нод на ядре X-Ray — по устройству близкая к
Marzban, но собранная под одну конкретную задачу: бесплатный VPN,
оплаченный рекламой, с единственным клиентом-приложением под Android и
головой, стоящей за блокировками.

Документ описывает систему целиком: что уже работает так, как задумано,
что менять и в каком порядке. Каждое утверждение о текущем поведении
проверено по коду, ссылки на файлы — рабочие.

---

## Кратко: три решения

Проект **уже** повторяет форму Marzban: голова хранит состояние и рисует
конфиги, ноды только выполняют. Менять форму не нужно. Нужно закрыть три
вещи, и первая из них ломает приложение раньше, чем оно выйдет в Play.

| № | Решение | Почему |
|---|---------|--------|
| 1 | **Изменения состава пользователей — через gRPC-API живого ядра, а не через `/restart`** | сейчас каждое подключение перезапускает X-Ray на ноде и рвёт установленные соединения всем остальным (§5) |
| 2 | **Свой агент ноды вместо `gozargah/marzban-node`** | чужой образ по тегу `:latest`, отвечает `503` без причины, не отдаёт логи — пять подряд разборов отказов упирались в это (§3) |
| 3 | **Голова — за пределами РФ, ноды остаются заграничными** | сейчас единственная точка, где лежат все ключи и вся база, стоит там, где действует блокировка (§12) |

Всё остальное в документе — либо описание того, что менять не надо, либо
следствия этих трёх решений.

## 1. Плоскости

Система делится не на «сервер и клиент», а на четыре плоскости с разными
требованиями к доступности. Разделение не декоративное: от того, какая
плоскость упала, зависит, что именно перестало работать.

| Плоскость | Где живёт | Что делает | Что будет, если упадёт |
|-----------|-----------|------------|------------------------|
| **Данных** | X-Ray на нодах, X-Ray на телефоне | несёт трафик пользователя | пользователь без интернета через VPN |
| **Управления** | голова ↔ агент ноды, mTLS | доставляет ноде желаемое состояние | **никто не отключается**; нельзя выдать новый конфиг и нельзя отключить просроченного |
| **Бизнеса** | только голова | реклама, время доступа, классы обслуживания, выбор ноды | нельзя купить время; уже купленное дорабатывает |
| **Операторская** | SSH-меню, CLI, `/admin`, Telegram-бот | человек управляет флотом | флот работает сам, вмешаться нельзя |

Из этого следуют два инварианта, которые нельзя нарушать ни одной новой
функцией.

**Инвариант 1. Нода ничего не знает.** На ноде нет ни базы, ни понятия
пользователя, ни понятия оплаченного часа, ни бизнес-логики. Нода — это
X-Ray плюс агент, который умеет запустить X-Ray с присланным конфигом.
Всё ценное — на голове. Отсюда следует, что нода одноразовая: её можно
снести и поставить заново, ничего не потеряв, и `bootstrap_node.sh`
именно так и делает — сначала вычищает предыдущую установку, потом
ставит.

**Инвариант 2. Работающий туннель не зависит от головы.** X-Ray на ноде —
подпроцесс, который меняется только по явной команде. Голова может лежать
сутки: все, кто подключён, продолжают работать. Это и есть причина, по
которой потеря канала управления (§6) — деградация, а не авария.

```
┌──────────────────────────── ГОЛОВА (панель) ────────────────────────────┐
│  FastAPI      PostgreSQL      планировщик      /admin      CLI + меню   │
│                                                                          │
│   доступ/реклама · выбор ноды · фабрика inbound'ов · пул SNI ·          │
│   обновления X-Ray · провижининг по SSH · шифрование секретов            │
└───────────┬──────────────────────────────────────────┬───────────────────┘
            │ mTLS + пиннинг сертификата               │ SSH — ровно один раз,
            │ (прямо, либо через Reality-туннель)      │ при заведении ноды
            ▼                                          ▼
┌──────── НОДА ────────┐  ┌──────── НОДА ────────┐  ┌──────── НОДА ────────┐
│ агент  →  X-Ray-core │  │ агент  →  X-Ray-core │  │ агент  →  X-Ray-core │
│ tc htb: full / grace │  │ tc htb: full / grace │  │ tc htb: full / grace │
└──────────┬───────────┘  └──────────┬───────────┘  └──────────┬───────────┘
           │  VLESS + Reality + XTLS Vision                     │
           └────────────────────┬──────────────────────────────┘
                                ▼
                     Android-приложение (X-Ray + tun2socks)
```

## 2. L0 — ядро X-Ray

Одно и то же ядро с обеих сторон, и это сознательно: протокол, который
защищает трафик клиента, используется и для служебных каналов, чтобы не
изобретать вторую маскировку.

**На ноде.** Один inbound на пару «порт + SNI»: `VLESS` поверх
`Reality` с потоком `xtls-rprx-vision`, outbound — `freedom`. Конфиг
целиком рисует голова (`head/app/node_manager/config_render.py`), нода не
дописывает в него ничего.

**Почему Reality.** Не нужен ни сертификат, ни собственный домен: ядро
предъявляет чужой настоящий TLS-хендшейк, а неаутентифицированного
пробника молча пересылает на реальный сайт, который действительно
отвечает. Значит, домен нельзя «сжечь» — он не наш. Цена в том, что
подставной домен должен быть жив, быстр с точки зрения **этой** ноды и
говорить TLS 1.3 + HTTP/2; отсюда пул SNI с пер-нодовыми пробами (§4).

**На телефоне.** То же ядро через `libXray` (MPL-2.0; `AndroidLibXrayLite`
из v2rayNG сознательно не берётся — он GPL-3.0 и утянул бы за собой всё
приложение). У X-Ray нет tun-inbound, поэтому пакеты с tun-устройства
читает `hev-socks5-tunnel` и отдаёт их в SOCKS-inbound ядра.

**Чего X-Ray не умеет, и что из этого следует.** Ограничения полосы на
пользователя в ядре нет: поле `speedLimit` в политике молча
игнорируется, `sendThrough` эффекта не даёт. Проверено, а не
предположено. Единственное, что видно снаружи ядра и на что можно
опереться, — порт. Отсюда вся конструкция классов обслуживания (§7).

## 3. L1 — агент ноды

### Что стоит сейчас

`gozargah/marzban-node:latest` в REST-режиме. Голова использует ровно
шесть вызовов (`head/app/node_manager/rest_client.py`):

| Вызов | Смысл |
|-------|-------|
| `POST /connect` | занять управление, получить `session_id` |
| `POST /ping` | продлить сессию |
| `POST /` | статус: `connected`, `started`, `core_version` |
| `POST /start` | поднять X-Ray с полным конфигом |
| `POST /restart` | остановить и поднять заново с новым конфигом |
| `POST /stop` | остановить |

Это малая часть того, что образ умеет, и вся часть, которая нам нужна.

### Четыре причины написать свой

Ни одна из них не про «чужой код плохой». Каждая стоила времени на этом
проекте.

1. **Тег `:latest`.** Плоскость данных всего флота меняется без нашего
   участия, в момент, который выбирает не наш релиз, а чужой. При этом у
   нас есть аккуратный процесс обновления X-Ray с подтверждением
   оператором (§4) — и он обходится стороной, потому что версию агента
   никто не спрашивает.

2. **`503` без причины.** Неудачный `/start` возвращает код и тело, в
   котором иногда написано, почему ядро не поднялось, — но не всегда, и
   не то. Со стороны головы это уже исправлено (`_check()` вкладывает
   тело в исключение), но исправить нечего, если нода причину не назвала.
   Отсюда прямое требование к своему агенту: **на неудачном старте вернуть
   stderr ядра.**

3. **Семантика сессий, которая нам не нужна.** `POST /connect` выбивает
   предыдущего владельца («Core control access was taken away from
   previous client»). Мы этим пользуемся при переключении прямого пути на
   туннельный — но контроллер у нас ровно один, и вся конструкция сессий
   существует ради сценария, которого в проекте нет.

4. **Логи недоступны.** Единственный способ узнать, что сказал X-Ray, —
   зайти на ноду по SSH. А SSH по замыслу используется ровно один раз, при
   заведении.

### Контракт своего агента (`skynode`)

Проволочный протокол остаётся тем же — это условие миграции без
переустановки флота. Добавляется то, чего не хватало.

```
POST /connect                 → { session_id, connected, started,
                                  core_version, agent_version,
                                  config_hash, core_started_at }
POST /ping
POST /                        → тот же статус
POST /start   { config }      → 200 либо 503 { error, core_stderr }
POST /restart { config }      → то же
POST /stop
GET  /logs?tail=N             → последние N строк stderr ядра     ← новое
POST /grpc/...                → проксирование API живого ядра     ← новое, §5
```

Четыре поля в статусе, которых не было, и зачем каждое:

- **`agent_version`** — версию агента можно проверять и обновлять тем же
  механизмом, что и X-Ray, вместо `:latest`.
- **`config_hash`** — хеш последнего применённого конфига. Голова хранит
  свой и сравнивает: расхождение означает, что нода живёт не тем
  состоянием, которое ей выдали.
- **`core_started_at`** — момент запуска ядра. Если он изменился, а голова
  ничего не перезапускала, значит, ядро упало и поднялось само — и все
  дельты, доставленные через gRPC после последнего полного пуша,
  потерялись (§5). Голова обязана перезалить конфиг целиком. Без этого
  поля такой обрыв обнаружить нечем.
- **`core_stderr` в теле ошибки** — та самая причина отказа.

Плюс поведение, а не поле: **если X-Ray умер, агент поднимает его с
последним полученным конфигом и честно сообщает об этом в статусе.**
Молчаливое самолечение хуже отсутствия самолечения — оно скрывает как раз
тот момент, после которого состояние головы и ноды разошлись.

Собирается из своего репозитория, версионируется тегом, ставится тем же
`bootstrap_node.sh`.

### Миграция

Контракт совместим, поэтому переезд идёт нодами, а не флотом:

1. у `nodes` появляется колонка `agent_kind` (`marzban` / `sky`);
2. голова спрашивает статус — свой агент называет `agent_version`, чужой
   молчит, отсюда и определяется вид;
3. тонкий путь (§5) включается только там, где агент свой; на остальных
   всё работает ровно как раньше;
4. нода переезжает при первом же повторном заведении, а оно и так
   вычищает предыдущую установку.

Отката не требуется: старая нода остаётся рабочей столько, сколько нужно.

## 4. L2 — голова

Единственное место, где есть состояние, и единственное, где есть решения.

| Модуль | Отвечает за | Инвариант, который держит |
|--------|-------------|---------------------------|
| `api/auth.py` | два токена: `X-Service-Token` (в APK) и `X-Admin-Token` (только на сервере) | приложению нельзя выдать админский токен: секрет внутри скачиваемого файла — публичный |
| `services/access.py` | доступ как отрезок времени, купленный вниманием | доступ не статус, а срок; выдаётся по одноразовому nonce |
| `services/enforcement.py` | отключение по истечении срока | час кончился — UUID уходит из конфига ноды; отсчёт в приложении это отображение, а не контроль |
| `services/config_selector.py` | какая нода и какой inbound достанутся пользователю | изолированную ноду новым не выдаём: обещать конфиг, который некому доставить, нельзя |
| `services/inbound_factory.py` | выбор порта и SNI для нового inbound'а | порт из набора своего класса; недавно «сгоревший» — в конец очереди |
| `services/tiers.py` | наборы портов классов `full` и `grace` | единственный источник правды: те же значения уезжают в `tc` на ноде |
| `services/tiering.py` | сверка класса пользователя с классом его inbound'а | оплативший не должен сидеть на низкоприоритетном порте |
| `services/fail_handler.py` | реакция на «не работает» от клиента | inbound умирает по счётчику в окне, а не с первой жалобы |
| `services/sni_discovery.py` | пул подставных доменов и пробы с каждой ноды | пригодность домена — свойство пары «нода ↔ домен», не глобальное |
| `services/xray_updates.py` | обновление ядра с подтверждением оператором | флот не перезапускается сам по чужому релизу |
| `services/provisioning.py` | заведение ноды: SSH → bootstrap → регистрация | при неудаче на голове не остаётся следов |
| `services/ssh_manager.py` | единственное место, где есть SSH | после заведения — только API |
| `services/certs.py`, `crypto.py` | mTLS-идентичность головы, шифрование паролей нод | дамп базы не даёт доступа к флоту |
| `node_manager/channel.py` | лестница состояний канала | потеря канала не отключает пользователей |
| `services/scheduler.py` | фоновые проходы | всё, что должно происходить само, происходит по расписанию, а не по случаю |

### Фоновые проходы

| Проход | Период | Зачем |
|--------|--------|-------|
| истечение доступа | 60 с | единственное, что реально заканчивает сессии |
| восстановление нод | 120 с | изолированную ноду никто не вызывает — снять изоляцию может только успешный вызов, значит, его надо делать нарочно |
| сверка классов | 30 мин | перевести пользователя на inbound своего класса |
| применение обновлений X-Ray | 60 с | действует по подтверждениям, даже когда проверка версий выключена |
| проверка версий X-Ray | 12 ч | предложить обновление, не применяя |
| обслуживание пула SNI | 24 ч | обновить кандидатов и пробы |

### Данные

`users` (доступ = `access_expires_at` + флаг `access_is_grace`) ·
`auth_identities` (telegram / device / phone / email) · `sessions`
(SHA-256 токена, не сам токен) · `ad_nonces` · `link_codes` ·
`nodes` (host, порт управления, ёмкость, занятые порты, PEM ноды,
состояние канала, зашифрованные SSH-доступы) · `inbounds` (порт, SNI,
транспорт, класс, ключи Reality, состояние, счётчики отказов, флаг
служебного канала) · `assignments` (кто на каком inbound'е, с каким
UUID) · `sni_candidates` + `sni_probes` · журналы событий и действий.

## 5. Управление изменениями: тонкий путь вместо толстого

**Это главный пункт документа.** Всё остальное можно доделывать по ходу;
это ломает приложение при первых же живых пользователях.

### Что происходит сейчас

У контрольного API ноды нет вызова «добавь одного пользователя». Любое
изменение — новый пользователь, отключённый, новый inbound после
блокировки — применяется одинаково: голова рисует **весь** желаемый
конфиг ноды и отправляет его.

```python
# head/app/node_manager/rest_client.py
path = "/restart" if current.started else "/start"
```

`/restart` — это остановка и запуск процесса X-Ray. Все установленные
через него соединения умирают.

Теперь сложим это с бизнес-моделью. Доступ покупается отрезками: 15 минут,
1 час, 2 часа. Значит, подключения — не редкое событие, а основной режим
работы: каждый пользователь возвращается по несколько раз в день, и
каждое возвращение — это `assign_config()` → `push_node_config()` →
`/restart`.

Ёмкость ноды по умолчанию — 200 человек. При средней сессии в час это
около 200 перезапусков в час, по одному каждые 18 секунд, и **каждый рвёт
соединения всем 200**. Даже на двадцати пользователях это перезапуск раз в
три минуты.

Честно о том, как это выглядит у пользователя: «VPN отключился» он не
увидит — клиент передоговорится. Он увидит, что скачивание обрывается,
видео встаёт, звонок рассыпается, и так каждые несколько минут. Диагноз
«интернет моргает» — самый трудный для поддержки, потому что и приложение,
и нода при этом отчитываются, что всё в порядке.

Ко всему прочему, отсюда же берётся частота отказов: чем чаще ядро
перезапускается, тем чаще какой-нибудь порт не успевает освободиться, и
тем чаще `/start` отвечает `503`.

### Что должно быть

Разделить изменения на два вида — по тому, меняют ли они **форму**
конфига или только **состав** пользователей.

| Вид изменения | Пример | Путь | Перезапуск ядра |
|---------------|--------|------|-----------------|
| **Форма** | новый inbound, мёртвый inbound убран, ротация SNI, обновление ядра | полный конфиг → `/restart` | да, редко |
| **Состав** | подключился пользователь, истёк час, аккаунт забанен | gRPC живого ядра | **нет** |

Тонкий путь — это встроенный в X-Ray `HandlerService`:
`AlterInbound` с операциями `AddUserOperation` / `RemoveUserOperation`,
адресованными по тегу inbound'а. Тег у нас уже есть — им служит `id`
inbound'а (`"tag": str(inbound.id)` в `config_render.py`), так что менять
в рисовании конфига ничего не нужно. Нужно добавить в конфиг служебную
секцию:

```json
"api":     { "tag": "api", "services": ["HandlerService", "StatsService", "LoggerService"] },
"policy":  { "levels": { "0": { "statsUserUplink": true, "statsUserDownlink": true } } },
"routing": { "rules": [ { "inboundTag": ["api"], "outboundTag": "api", "type": "field" } ] }
```

и inbound `dokodemo-door` на localhost с тегом `api`. Наружу этот порт не
выставляется никогда: доступ к нему идёт через агента, по тому же mTLS,
что и остальное управление.

Ровно так это устроено в Marzban — и это единственная причина, по которой
Marzban держит тысячи пользователей на ноде.

### Что при этом обязательно предусмотреть

Изменения, внесённые через gRPC, **не попадают в файл конфига**. Если ядро
перезапустится — своим ли решением агента, падением, обновлением — оно
поднимется с тем конфигом, который ему присылали последним, и всех, кто
был добавлен дельтами после, там не будет.

Поэтому:

1. голова рисует полный конфиг **со всеми текущими пользователями** —
   значит, любой полный пуш сам по себе приводит ноду в актуальное
   состояние;
2. агент отдаёт `core_started_at` и `config_hash` (§3);
3. проход восстановления нод (те же 120 секунд, отдельный механизм не
   нужен) сравнивает их с сохранёнными и при расхождении делает полный
   пуш.

И правило отката: **если gRPC-вызов не прошёл — делаем полный пуш.**
Тонкий путь оптимизация, а не единственная дорога; в худшем случае
система ведёт себя как сегодня.

### Что упрощается следом

- **`enforcement.sweep_expired()`** сегодня группирует отключаемых по
  нодам, чтобы не перезапускать ноду по разу на человека. С тонким путём
  группировка перестаёт быть необходимостью — но остаётся полезной, так
  что менять её не нужно, только снять из неё логику отката.
- **`fail_handler`** метит inbound мёртвым — это изменение формы, полный
  пуш, всё как было.
- **`config_selector.assign_config()`** перестаёт быть дорогой операцией,
  и вместе с этим уходит целый класс отказов «нода не приняла конфиг,
  потому что была занята перезапуском».

## 6. Канал управления

### mTLS с пиннингом, а не с УЦ

Агент ноды генерирует самоподписанный сертификат при первом запуске.
Голова забирает его во время заведения и с этого момента принимает от
этой ноды **только его**. Своего удостоверяющего центра нет и не нужно:
нод десятки, а не тысячи, и каждая заводится через SSH — момент, в
который сертификат можно взять из первых рук.

Одна тонкость стоила отдельного разбора и заслуживает записи: у такого
сертификата нет IP в SAN, а `httpx` с `verify=<путь>` включает и проверку
имени хоста — получается `IP address mismatch` на верном сертификате.
Правильное решение — не отключать проверку, а собрать контекст явно:

```python
context = ssl.create_default_context(cafile=certs.ca_cert)
context.load_cert_chain(certs.client_cert, certs.client_key)
context.check_hostname = False        # имени нет и быть не может
context.verify_mode = ssl.CERT_REQUIRED   # но сертификат обязан быть тем самым
```

Разница принципиальная: чужой валидный сертификат по-прежнему
отвергается.

### Лестница состояний

Состояние канала — свойство связи «голова → нода», а не ноды. Пока идёт
лестница, X-Ray на ноде обслуживает всех, кто уже подключён.

| Состояние | Как попадаем | Что делает голова |
|-----------|--------------|-------------------|
| `active` | прямой вызов проходит | пользуется прямым путём |
| `degraded` | 3 отказа прямого пути подряд | поднимает локальный клиент X-Ray, дозванивается до **служебного** Reality-inbound'а ноды и пускает те же REST-вызовы через полученный SOCKS |
| `isolated` | 3 отказа туннельного пути подряд | шлёт оператору сигнал в Telegram, новых пользователей на ноду не ставит, продолжает пробовать оба пути |

Туннель — не вторая техника обхода, а та же самая: голова прикидывается
собственным клиентом. Для наблюдателя это обычная сессия обычного
пользователя VPN — служебный трафик не получает маскировку слабее той,
что уже защищает клиентов.

Служебный inbound (`is_control_channel=True`) — ровно один на ноду, с
единственным клиентом (сама голова), никогда не выдаётся пользователю,
никогда не помечается мёртвым и всегда попадает в конфиг.

**Почему нужен отдельный проход восстановления.** Изолированную ноду
`config_selector` пропускает, то есть ей никто не звонит. А снять
изоляцию может только успешный вызов. Без нарочного прохода нода,
однажды признанная недоступной, оставалась бы вне ротации навсегда —
её случайно задевала только двенадцатичасовая проверка версий X-Ray.
Отсюда `node_recovery_loop` каждые 120 секунд.

## 7. Классы обслуживания и `tc`

Класс — свойство **inbound'а**, а не ноды. Каждая нода обслуживает всех;
различает людей порт, потому что порт — единственное, что видит `tc`.

| Класс | Кто туда попадает | Порты | Запасной диапазон |
|-------|-------------------|-------|-------------------|
| `full` | посмотрел рекламу и оплатил этот час вниманием | 443, 2053, 2087 | 20000–39999 |
| `grace` | рекламу показать не удалось, пустили всё равно | 8443, 2083, 2096 | 40000–59999 |

Все порты — обычные HTTPS-порты, так что listener Reality на любом из них
ничем не выделяется, а деление между классами снаружи ничего не значит.

На ноде — `htb` с двумя приоритетными классами, фильтры по исходящему
порту. Оба класса могут разгоняться до полной полосы, так что при
свободном канале никто ничего не теряет; разница проявляется ровно тогда,
когда канал занят. Настраивается один раз при заведении: наборы портов не
меняются, меняется только то, какой порт внутри набора сейчас в работе, —
поэтому при ротации inbound'ов на ноде **ничего запускать не надо**.

Значения не продублированы: `services/tiers.py` — единственный источник, и
он же передаёт их в `bootstrap_node.sh`. Если бы они расходились, приоритет
молча перестал бы работать — отказ, который никак не проявляется, кроме
жалоб на скорость.

**Место под платный класс.** Подписка планируется позже, через бота.
Архитектурно она уже помещается: доступ и так измеряется временем, так
что платная выдача — это `grant_manual()` с другим классом. Понадобится
третий набор портов, третий класс `htb` и переустановка правил `tc` на
нодах — то есть один проход по флоту, без изменения модели.

## 8. Экономика доступа

Сервис живёт на рекламе, поэтому доступ — не статус, который у человека
есть, а отрезок времени, купленный вниманием.

| Пакет | Что показываем | Сколько даёт |
|-------|----------------|--------------|
| `short` | interstitial | 15 минут |
| `hour` | rewarded | 1 час |
| `double` | rewarded ×2 | 2 часа (по часу за просмотр) |

Минуты начисляются **за просмотр, а не за пакет**: посмотревший один
ролик из двух и ушедший сохраняет заработанный час, и не нужно отдельно
рассуждать про брошенные пакеты. Потолок накопления — 24 часа.

Три неудобных вопроса, на которые модель отвечает прямо:

**Откуда известно, что рекламу посмотрели?** Со слов клиента —
ниоткуда. Модифицированный APK скажет что угодно. Одноразовый
короткоживущий nonce, выданный головой за минуту до, поднимает цену — одну
записанную HTTP-пару нельзя проигрывать вечно, — но настоящий ответ один:
серверная проверка, когда рекламная сеть звонит нам сама
(`redeem_verified`, переключатель `AD_SSV_REQUIRED`).

**Что если рекламу не показать?** Заполняемость не бывает стопроцентной.
Гарантированный отказ означал бы, что наш сбой — полный: VPN, который не
подключается, это не «ухудшенный VPN». Поэтому неудача даёт короткий
льготный отрезок на **низком** классе — намеренно хуже настоящего, чтобы
не стать способом пропускать рекламу, и с ограничением по частоте.

**Что с ботом?** Telegram-боты не умеют показывать rewarded-видео —
такого SDK нет. Значит, бот в этой экономике участвовать не может, и любая
выдача через него — дыра в обход рекламы. Отсюда: бот служебный, отвечает
только явно разрешённым чатам, каждая выдача записывается с автором.

**Кто на самом деле отключает.** `enforcement.py`. Нода не знает, что
такое час; она крутит тот конфиг, который ей дали, а в конфиге —
список UUID. Пользователь подключён ровно до тех пор, пока его UUID там
есть. Отсчёт в приложении и автоотключение по таймеру — это отображение;
на модифицированной сборке они просто не выполнятся.

## 9. Egress: выход к Telegram

Telegram заблокирован там, где стоит голова, а бот и сигнализация о
проблемах ходят именно туда. Выход — через собственный флот.

Устройство намеренно скучное: **egress — обычный пользователь.** У него
свой аккаунт, он садится на обычный inbound рядом с живыми клиентами и на
проводе от них неотличим. Значит, вся обработка отказов, написанная для
людей, работает для него без единой строчки специального кода: когда нода
перестаёт нести его трафик, он жалуется ровно так же, как телефон, и
голова переставляет его тем же путём.

Практически: контейнер поднимает локальный SOCKS, каждые 60 секунд
проверяет через него `api.telegram.org`, после трёх неудач подряд
сообщает голове и перезапускается с конфигом другой ноды.

**Оговорка, которую нельзя замалчивать.** Если сигнал о том, что с флотом
плохо, идёт через флот, то в худшем сценарии он не дойдёт. Единственное
честное решение — закрепить egress на сервере **вне** флота
(`EGRESS_VLESS_URL`); тогда переключение отключается, зато тревога не
зависит от того, о чём она.

## 10. L4 — Android-приложение

Один экран, одна кнопка, тёмная тема. Ни выбора страны, ни списка
серверов: выбор — задача головы, наружу отдаётся только рабочая ссылка.

### Что приложение просит у головы

| Метод | Зачем | Токены |
|-------|-------|--------|
| `POST /api/v1/auth/device` | анонимная регистрация при первом запуске | сервисный |
| `POST /api/v1/me/connect` | получить `vless://` | сервисный + Bearer |
| `POST /api/v1/me/report-failure` | «не работает» → другой inbound/нода | сервисный + Bearer |
| `GET /api/v1/me` | сколько времени осталось, класс | сервисный + Bearer |
| `POST /api/v1/me/ad/prepare` | nonce на прогон пакета | сервисный + Bearer |
| `POST /api/v1/me/ad/complete` | засчитать просмотр | сервисный + Bearer |
| `POST /api/v1/me/ad/unavailable` | рекламы нет, взять льготный отрезок | сервисный + Bearer |
| `POST /api/v1/me/link/start` | код привязки к Telegram | сервисный + Bearer |
| `GET /api/v1/routing-policy` | что пускать мимо туннеля | сервисный + Bearer |

Девять методов, и ни один не действует от чужого имени — это и есть
граница того, что можно доверить токену из APK. Всё остальное (21 метод:
ноды, выдачи, обновления, SNI, очередь конфигов) — за админским токеном,
который никогда не покидает сервер.

Идентификатор устройства генерирует **голова**, не клиент: выбранный
клиентом идентификатор — угадываемый, а угадать его значит получить чужой
аккаунт.

### Как приложение вообще дозванивается до головы

Сейчас: несколько адресов из `BuildConfig.HEAD_API_URL`, отладочная
подмена, запоминание последнего сработавшего. На следующую ошибку
транспорта клиент идёт к следующему адресу; на HTTP-ошибку — не идёт,
потому что голова ответила, и превращать один честный отказ в три
бессмысленно.

Этого мало, если заблокируют саму голову. Правильное развитие —
**опубликовать API головы через флот**: добавить на ноды inbound, который
за тем же Reality проксирует запросы к голове. Тогда путь до головы
получает ту же маскировку, что и пользовательский трафик, а адрес входа
можно менять так же часто, как inbound'ы. Это единственная существенная
архитектурная добавка, которую требует приложение и которой ещё нет.

### Переподключение внутри оплаченного часа

Оплаченный час не должен зависеть от того, дозвонились ли мы до головы в
эту минуту. Приложение хранит последний выданный конфиг и время, до
которого он действителен, и внутри этого срока переподключается им же, не
спрашивая голову. Обращение к голове нужно только чтобы **купить** время,
а не чтобы им пользоваться.

### Раздельное туннелирование

Три слоя, потому что каждый ловит то, что пропускают остальные: правила по
TLD (`.ru`, `.рф`, `.su`, `.moscow`, `.tatar`), поимённые исключения для
российских сервисов на иностранных доменах (vk.com, 2gis.com, okko.tv,
premier.one …) и `geoip:ru` для адресации по IP. Четвёртый слой живёт на
клиенте: целые приложения, исключённые по имени пакета, — для тех, что
сами смотрят на сеть и отказываются работать при поднятом VPN, чему
никакое правило маршрутизации помочь не может.

Отдаётся с головы, а не зашивается в APK: сервис, который начал вести себя
странно, надо уметь перевести на прямой маршрут сегодня, а не после
ревью в Play. Та же таблица лежит в приложении как запас — для первого
запуска и для случая, когда голова недоступна.

### Что приложению даст §5

Помимо того, что перестанет «моргать»: `StatsService`, включённый ради
тонкого пути, попутно даёт голове настоящие счётчики трафика на
пользователя. Это и материал для будущей платной подписки, и способ
замечать злоупотребления, которого сейчас нет вовсе.

### Чего в приложении ещё нет

- нативные библиотеки (`libXray`, `hev-socks5-tunnel`) не вложены —
  сборка компилируется и честно сообщает, что подключиться не может;
- модуль `:app` ни разу не собирался: в этой среде нет Android SDK;
- `POST_NOTIFICATIONS` объявлено в манифесте, но не запрашивается в
  рантайме — на Android 13+ уведомление о работающем VPN не покажется.

## 11. Операторская плоскость

Четыре входа, и у каждого своя причина существовать.

| Вход | Для чего | Почему не обойтись остальными |
|------|----------|-------------------------------|
| **SSH-меню** (`freeskyvpn`) | завести первую ноду, чинить, когда всё остальное не отвечает | остальные три требуют работающей головы и работающей сети — а первая нода нужна как раз до этого |
| **CLI** (`python -m app.cli`) | то же самое из скриптов, `--json` | меню — обёртка над ним, а не отдельная логика |
| **`/admin`** | повседневное: ноды, люди, SNI, обновления, журналы | таблицы и история читаются глазами, а не в терминале |
| **Telegram-бот** | подтвердить обновление X-Ray, выдать тестовый доступ | приходит само, когда оператор не за компьютером |

Правило, которое держит это в порядке: **бизнес-логики вне головы нет.**
Меню не знает ничего о нодах — оно вызывает CLI внутри контейнера. Бот не
знает ничего о доступе — он ходит в API головы. Иначе одно и то же
решение оказалось бы записано в четырёх местах и разошлось бы в трёх.

Раньше замыкался круг: чтобы завести ноду, нужен был бот; чтобы бот
заработал из РФ, нужна была нода. SSH-меню его размыкает.

## 12. Где стоит голова

Сейчас: голова — со всей базой, всеми ключами, mTLS-идентичностью и
шифрованными доступами к нодам — стоит в РФ, ноды заграничные.

Это перевёрнуто. Единственный элемент, потеря которого необратима, стоит
там, где действует блокировка; элементы, которые по замыслу одноразовые и
восстанавливаются за минуты, — там, где её нет. Из этого расположения
растёт добрая половина сложности документа: и лестница состояний канала
(§6), и Reality-туннель, и egress (§9) существуют потому, что голова
сидит за блокировкой.

**Рекомендация: вынести голову за пределы РФ.** Что меняется:

- канал управления перестаёт быть проблемой — прямой путь работает,
  туннель остаётся страховкой, а не рабочим режимом;
- egress становится не нужен: Telegram доступен напрямую;
- база и ключи оказываются вне досягаемости внесудебного изъятия;
- раздельное туннелирование (§10) не меняется вообще — оно про клиента, а
  не про голову.

Что нужно сделать: перенести том Postgres, `secrets/` и `.env`. Ноды
переустанавливать не нужно, если сохранить `secrets/head_client_key.pem`
— именно ему они доверяют. Потеря `SECRETS_KEY` делает сохранённые
SSH-доступы нод нечитаемыми; потеря клиентского ключа означает
переустановку всего флота.

## 13. Порядок работ

Отсортировано по тому, что чем разблокируется, а не по трудоёмкости.

| № | Работа | Что закрывает |
|---|--------|---------------|
| 1 | Свой агент ноды с честной причиной отказа и `/logs` (§3) | текущий не поднимающийся `503` перестанет быть загадкой; появляется место, куда встраивать всё дальнейшее |
| 2 | `agent_version`, `config_hash`, `core_started_at` + сверка в проходе восстановления | голова начинает замечать расхождение с нодой |
| 3 | Тонкий путь через gRPC (§5) | приложение перестаёт «моргать»; нода начинает держать сотни людей вместо десятков |
| 4 | Перенос головы за пределы РФ (§12) | убирает причину половины сложности |
| 5 | Публикация API головы через флот (§10) | приложение продолжает дозваниваться, когда голову заблокируют |
| 6 | Серверная проверка рекламы (`AD_SSV_REQUIRED`) | доход перестаёт зависеть от честности клиента |
| 7 | Вложить нативные библиотеки, собрать `:app`, запросить `POST_NOTIFICATIONS` | приложение впервые подключается по-настоящему |
| 8 | Платный класс: третий набор портов и класс `tc` | подписка через бота |

Пункты 1–3 — одна работа по существу и делаются вместе.

## 14. Чего архитектура сознательно не делает

Список нужен не меньше остальных: без него каждое из этих решений будет
предложено заново.

- **Нет выбора страны и списка серверов у пользователя.** Одна кнопка.
  Выбор — задача головы; список серверов, показанный пользователю, — это
  список серверов, показанный тому, кто их блокирует.
- **Нет бизнес-логики на нодах.** Нода одноразовая и ничего не знает.
- **Нет своего удостоверяющего центра.** Пиннинг сертификата на десятках
  нод проще и строже, чем УЦ.
- **Нет мультиарендности.** Один оператор, один флот. Модель доступа,
  модель нод и админка это предполагают.
- **Нет умного диффа конфигов.** Ровно два пути: полный конфиг при
  изменении формы, gRPC при изменении состава. Третий — источник
  расхождений, которые нечем обнаружить.
- **Нет доверия клиенту.** Ни отсчёт времени, ни просмотр рекламы, ни
  раздельное туннелирование не считаются доказанными оттого, что о них
  сообщило приложение.
