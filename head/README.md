# FreeSkyVPN — головной сервер

Реализует фазы 0–4 из [чертежа](../README.md): схема БД, API, устойчивый
канал управления нодами, выбор конфигов с реакцией на блокировки, биллинг.
MVP-клиент к нему — [Telegram-бот](../bot/README.md).

## Локальный запуск

```bash
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"

cp .env.example .env   # и укажите реальный DATABASE_URL

# применить схему (нужен настоящий Postgres)
.venv/bin/alembic upgrade head

.venv/bin/uvicorn app.main:app --reload
```

## Тесты

Модели и рендер конфига проверяются на SQLite in-memory, без реального
Postgres:

```bash
.venv/bin/pytest
```

## Структура

- `app/db/models` — схема (пользователи/идентификация, тарифы, ноды/инбаунды, SNI-пул, логи, outbox)
- `app/api/routers` — `/health` (открыт), остальное под сервисным токеном:
  `/auth/telegram`, `/nodes`, `/connect`, `/report-failure`, `/plans`,
  `/me/*` (подключение, реклама, привязка), `/pushes/*`,
  `/xray-updates/*`
- `app/api/auth.py` — сервисный токен между головой и её клиентами (бот, провижининг)
- `app/node_manager` — транспорт до ноды:
  - `rest_client.py` — клиент REST-контракта marzban-node (connect/start/restart/stop)
  - `config_render.py` — сборка полного Xray-конфига ноды из её inbounds
  - `reality_tunnel.py` + `channel.py` — устойчивость канала управления при блокировке (см. §06а ниже)
- `app/services` — логика (фаза 2):
  - `config_selector.py` — выбор ноды и inbound под пользователя
  - `fail_handler.py` — обработка «не работает»: порог, смерть inbound, миграция всех задетых
  - `inbound_factory.py` — выбор порта/SNI, генерация Reality-ключей
  - `transports.py` — что реально можно ротировать (см. §07а ниже)
  - `access.py` — пакеты времени за рекламу, запасной доступ, ручные выдачи (см. §09а)
  - `enforcement.py` — то, что реально отключает по истечении времени (см. §09б)
  - `sni_discovery.py` — автоподбор и верификация SNI (см. §07в)
  - `tiers.py` + `tiering.py` — наборы портов по классам обслуживания и приоритет (см. §10а)
  - `xray_updates.py` — поиск обновлений Xray и их установка по согласию (см. §11а)
  - `scheduler.py` — фоновые задачи: свежесть SNI-пула, пересчёт размещения,
    поиск и установка обновлений Xray
- `migrations/` — Alembic; `0001_initial` — единая ревизия из `Base.metadata`, дальше — обычные диффы

## §06а — устойчивость канала управления (доп. к чертежу)

Голова физически в РФ → именно её исходящее соединение к ноде попадает под
DPI/TSPU, а не наоборот. `NodeChannelState` на каждой ноде: `active` (прямой
REST) → `degraded` (тот же REST, но через локальный VLESS+Reality клиент
головы, туннелирующий к отдельному, невидимому пользователям inbound
ноды — переиспользуем протокол, а не изобретаем новый) → `isolated` (не
достучались ни туда, ни туда — алерт админу в Telegram, единственный канал,
не зависящий ни от одной ноды). Существующие пользователи ноды не
затрагиваются: Xray на ноде продолжает работать независимо от состояния
канала управления, недоступность канала блокирует только новые пуши.

**Важная поправка к первой версии чертежа**: реальный Gozargah/Marzban-node
использует не gRPC, а REST (HTTPS + mTLS клиентский сертификат) или, как
альтернативу, RPyC — этот проект стандартизируется на REST (протокол по
умолчанию у marzban-node). Контроль полностью «толстый»: нет вызова
«добавить одного пользователя», только «вот весь желаемый конфиг, запусти».
Отсюда и `config_render.py` — при любом изменении состава пользователей
голова пересобирает весь конфиг ноды целиком и пушит через `/restart`.

## §07а — что реально можно ротировать (доп. к чертежу)

В ТЗ было «порт, SNI и транспорт меняются исходя из ситуации». Проверено на
Xray-core 26.3.27:

- **порт** — свободно. Сначала обычные HTTPS-порты (443, 8443, 2053…), затем
  случайный высокий. Порты **переиспользуются**: мёртвый inbound выпадает из
  конфига ноды, так что его порт реально свободен, а запас «естественно
  выглядящих» портов слишком мал, чтобы списывать их навсегда после одной
  блокировки. Единственное исключение — порт, умерший только что: пока не
  истекло окно `INBOUND_FAIL_WINDOW_MINUTES`, он понижен в приоритете, иначе
  замена мгновенно воспроизвела бы ту же блокировку.
- **SNI** — свободно, пул подбирается автоматически (см. §07в ниже).
- **транспорт** — ограниченно. Reality не поддерживает WebSocket вообще:
  `REALITY only supports RAW, XHTTP and gRPC for now`. Так что пространство
  ротации — RAW(tcp)/XHTTP/gRPC, а `xtls-rprx-vision` остаётся только на RAW
  (Vision склеивает сырой TCP-поток, под gRPC/XHTTP-обёрткой смысла не имеет).
  RAW+Vision — дефолт для всех inbound'ов.

Тест `tests/test_xray_config_accepted.py` прогоняет отрендеренные конфиги
через настоящий бинарь xray, чтобы рассинхрон рендера и клиентской ссылки
ловился здесь, а не на проде (пропускается, если бинаря нет —
`XRAY_TEST_BINARY=/path/to/xray pytest`).

## §07б — реактивная детекция

Единственный источник сигнала — кнопка «не работает». Ниже порога
(`INBOUND_FAIL_THRESHOLD`, окно `INBOUND_FAIL_WINDOW_MINUTES`) переезжает
только пожаловавшийся: его проблема может быть локальной. На пороге inbound
объявляется мёртвым для всех, кто на нём сидит, каждый из них переселяется, и
им ставится задача на доставку в `config_pushes` — сам пожаловавшийся получает
конфиг синхронно в ответе, поэтому в outbox не попадает. Если на ноде за то же
окно умирает несколько inbound'ов, сожжённой считается вся нода и пользователи
уезжают на другую: новый порт и SNI не спасут заблокированный IP.

`config_pushes` — это outbox: голова решает, кому нужен новый конфиг, но сама
до пользователей не дотягивается. Доставку разбирает клиентский слой —
Telegram-бот в фазе 3, push-уведомления в Android-фазе.

## §09а — доступ покупается вниманием (замена биллингу)

Платной подписки нет. При нажатии «включить» пользователь выбирает, на
сколько:

| пакет | время | чем платит |
|---|---|---|
| `short` | 15 минут | один пропускаемый ролик |
| `hour` | 1 час | один полный ролик |
| `double` | 2 часа | два полных ролика |

Время кончилось — VPN выключается, и включить снова можно только выбрав
пакет заново. Время не кончилось, а пользователь сам выключил VPN — включает
обратно без рекламы: эти минуты уже оплачены, брать за них второй раз
нельзя.

`app/services/access.py` — единственное место, где живёт эта модель.

**Время начисляется за просмотр, а не за пакет.** Кто посмотрел первый из
двух роликов и закрыл приложение, оставляет себе час. Взять просмотр и не
дать ничего — единственное поведение, которое гарантированно отучает
смотреть.

**Пакет выбирает сервер, а не клиент.** Токен, выданный перед роликами,
несёт код пакета; клиент, который мог бы назвать свою награду, назвал бы
большую.

**15 минут никем не проверяемы.** Пропускаемый interstitial не имеет
сигнала завершения — ни у клиента, ни у сети. Поэтому он покупает меньше
всего времени. По расчёту (`economics/`) он всё равно выгоднее часового
пакета за час обслуживания, пока его eCPM выше ~30 ₽.

**Почему вообще ограничение.** Расходы растут от трафика, выручка — от
внимания. Это несвязанные величины: пользователь на 200 ГБ в месяц
посмотрит примерно столько же рекламы, сколько на 2 ГБ, а стоит в сто раз
дороже. При подписке такие конвертируются в платящих; без подписки
конвертировать некуда, и единственное, что стоит между сервисом и убытком,
— ограничение. Расчёт в `economics/`.

**Как проверяется, что рекламу посмотрели.** С клиента — никак. Изменённый
APK может звать «я посмотрел» сколько угодно. Nonce поднимает цену:
на каждую выдачу нужен токен, который голова выдала минуту назад,
одноразовый и короткоживущий, так что записанный HTTP-вызов не превращается
в бесконечный генератор доступа. Настоящий ответ — проверка на стороне
рекламной сети: `redeem_verified` и `AD_SSV_REQUIRED`, после которого слово
клиента не принимается вообще.

**Что если рекламы нет.** Заполнение не бывает стопроцентным, сеть бывает
недоступна. Если считать «нет ролика» за «нет сервиса», их авария
становится нашей — полной, а не частичной. Поэтому неудача выдаёт короткий
запасной доступ в классе `grace`, намеренно хуже настоящего, чтобы не стать
способом пропустить рекламу. `ACCESS_GRACE_MINUTES=0` выключает это для
тех, кто предпочтёт отказ.

**Почему бот раздаёт доступ по списку.** Telegram-боты не умеют показывать
rewarded video — такого SDK нет. Значит бот не может участвовать в том, что
оплачивает серверы, и любой доступ через него — дыра в обход рекламы.
Отсюда `TELEGRAM_ALLOWED_CHAT_IDS` и запись каждой выдачи с источником.

## §09б — что на самом деле отключает пользователя

Дыра, которую пришлось закрыть отдельно: всё остальное только не давало
**выдать** конфиг. `/me/connect` отказывает без доступа, свип размещения
переводит просроченного в медленный класс — но ни то, ни другое не трогает
уже поднятый туннель.

Нода не знает ни про часы, ни про рекламу. Она крутит тот Xray-конфиг,
который ей последним отдали, а в конфиге перечислены UUID клиентов.
Пользователь подключён ровно до тех пор, пока его UUID там есть, — то есть,
до появления `enforcement.py`, бесконечно. Один ролик покупал безлимитный VPN.

Отключение выглядит так: освободить назначение, пересобрать конфиг ноды без
этого UUID, отправить. Xray роняет клиента на рестарте.

Три детали, каждая проверена тестом:

- **Один пуш на ноду, а не на пользователя.** Каждый пуш перезапускает Xray
  ноды; пуш на каждого просроченного клал бы загруженную ноду по нескольку
  раз ради одного логического изменения.
- **Недоступная нода сохраняет назначения.** База, в которой написано
  «отключён», пока туннель работает, — это база, которая больше никогда не
  попробует. Правда лежит в конфиге ноды.
- **Контрольный инбаунд не трогается.** Убрать его — обрезать голове
  собственный запасной путь до ноды.

Автоотключение в приложении — вежливость, а не принуждение: изменённая
сборка просто не станет его делать. Сессию заканчивает голова.

## §07в — автоподбор SNI

Пул больше не набивается руками. Две половины вопроса «годится ли домен как
Reality dest» автоматизируются по-разному, и это стоит различать:

- **Проверяемо машиной.** Домен действительно отвечает на 443, договаривается
  до TLS 1.3, предлагает h2 и предъявляет доверенный сертификат на себя.
  Причём проверяется это **с позиции ноды**, а не головы: Reality
  ретранслирует хендшейк пробера с ноды на этот хост, поэтому медленный или
  битый оттуда dest портит каждое соединение. Пробы идут через уже
  существующий Reality-туннель управления (`tunnel_socks_proxy`), который и
  так выходит в сеть с ноды. Вердикты хранятся по паре (нода, домен) —
  домен, быстрый из Амстердама, бесполезен из Сингапура.
- **Не проверяемо машиной.** Выглядит ли трафик к домену обыденно. Это даёт
  не проба, а **источник**: домены берутся из рейтинга популярности, поэтому
  в пул попадает то, что и так посещают массово. `example.com` проходит все
  технические проверки, но отсекается тем, откуда берутся кандидаты, а не
  пробой. Самая верхушка рейтинга пропускается (`SNI_SKIP_TOP_RANKS`):
  крупнейшие платформы вероятнее всего обрабатываются цензором отдельно, а
  часть их в РФ и так заблокирована.

Эмпирическая поправка остаётся прежней: `burn_count` считает, сколько раз
inbound на домене умирал, и выбор предпочитает наименее сожжённый. Подбор
предлагает — история блокировок отбраковывает.

Обновление пула идёт фоново (`app/services/scheduler.py`, раз в
`SNI_REFRESH_INTERVAL_HOURS`); есть и ручные ручки `/api/v1/sni/*`.

## §10а — два класса обслуживания: приоритет, а не разделение

**Поправка к чертежу, найденная замерами.** В плане было «ограничение скорости
через Xray user-level policy». Такого механизма нет: поле `speedLimit`,
которое встречается в руководствах, Xray молча игнорирует. Проверено не
чтением конфига (парсер принимает и заведомо выдуманные поля — отдельная
ловушка), а замером пропускной способности: с `speedLimit=1` и без него
скорость одинаковая, ровно как у бессмысленного поля. Вторая идея — развести
тарифы по разным исходящим адресам через `sendThrough` — тоже не работает:
адрес не применяется, а несуществующий адрес не ломает соединение, хотя
обязан был бы.

**Ноды общие.** Каждая обслуживает всех. Единственное, что о трафике
пользователя видит нода, — порт, на который он подключился. Поэтому класс
обслуживания живёт на inbound'е: каждому классу принадлежит свой набор портов
(`app/services/tiers.py`), а `tc` на ноде настраивается один раз при
провижининге на два класса с разным приоритетом.

Различие проявляется ровно тогда, когда канал загружен:

- оба класса могут разгоняться до полного канала, так что при простое одного
  тарифа полоса не пропадает;
- гарантии разделены 70/30, и при конкуренции `htb` обслуживает
  высокоприоритетный класс первым — те, кто посмотрел рекламу (`full`),
  получают полосу, запасной доступ (`grace`) — остаток;
- `fq_codel` внутри каждого класса не даёт одному тяжёлому пользователю
  задушить соседей по тому же тарифу.

Наборы портов передаются в bootstrap **с головы**, а не зашиты на ноде: иначе
фильтры `tc` и порты, которые голова раздаёт, могли бы разойтись, и приоритет
тихо перестал бы работать. Тест проверяет, что наборы не пересекаются и что
любой выданный порт (включая fallback-диапазон) отображается обратно в свой
тариф.

**Приоритет при приёме.** Кроме полосы, есть очередь на вход: у ноды есть
ёмкость, и `grace` перестаёт приниматься на `FREE_ADMISSION_RATIO` (по
умолчанию 80%) от неё. Остаток держится для тех, кто посмотрел рекламу.
Отказ при этом внятный, а не пустая ошибка.

Классы назывались `paid`/`free`, пока планировалась подписка. Наборы портов
и правила `tc` не изменились — поменялось только то, что решает, кто в каком
классе, — поэтому переименование не потребовало перенастройки нод.

**Что не проверено:** сам `tc`. В этой среде нет `ip` и сетевых namespace, так
что скрипт, который генерирует правила, проверен на корректность вывода, но не
применён к живому интерфейсу. Это нужно подтвердить на настоящей ноде.
Головная часть — выбор тарифа, портов, ёмкость, пересчёт — покрыта тестами.


## §11а — обновления Xray: голова находит, человек решает

Xray на нодах устаревает сам по себе, а обновлять его вручную по SSH — ровно
та работа, которой в этом проекте быть не должно. Но и полностью
автоматическим обновление быть не может: оно пересоздаёт контейнер на ноде, и
все живые подключения на ней рвутся. Поэтому механизм разделён на две
половины, между которыми стоит строка в базе (`node_updates`):

1. **Поиск.** Раз в 12 часов голова спрашивает у GitHub последний релиз
   Xray-core, а у каждой активной ноды — её `core_version` (через тот же
   канал управления, что и всё остальное, включая Reality-туннель при
   блокировке прямого). Где новее — заводится строка со статусом `pending`.
   Ничего не запускается.
2. **Решение и установка.** Человек подтверждает в Telegram или в админке;
   строка переходит в `approved`, и отдельный цикл раз в минуту берёт
   **по одной ноде за раз** и выполняет `provisioning/update_node.sh` по SSH.

Что важно в деталях:

- **Сравнение версий числовое, а не строковое.** Xray перешёл с `1.x` сразу
  на `25.x`, поэтому лексикографически `9.1.0` «новее» `26.3.27`, и все ноды
  выглядели бы вечно актуальными.
- **Неизвестная версия не считается устаревшей.** У ноды с упавшим каналом
  управления версию не спросить, а предлагать перезапуск того, до чего мы не
  дозвонились, — плохая идея.
- **GitHub недоступен — это не сбой.** Голова стоит в РФ; неудачный запрос
  означает «в этот раз новостей нет», а не упавшую задачу. Страница админки
  вообще не ходит в сеть при рендере: иначе на сервере без доступа к GitHub
  она открывалась бы по таймауту.
- **Xray приезжает внутри образа `marzban-node`, а не из XTLS напрямую.**
  Образ может отставать от релиза. Тогда обновление проходит успешно, но
  версия остаётся прежней — это фиксируется примечанием, а не ошибкой, и
  повторно голова спросит только через сутки. Без этого одна неподхваченная
  версия давала бы уведомление каждые 12 часов, и человек научился бы их
  игнорировать.
- **`update_node.sh` не повторяет `docker run`**, а перезапускает
  `/usr/local/sbin/freeskyvpn-start-node.sh`, оставленный bootstrap'ом. Иначе
  обновление могло бы тихо пересоздать контейнер с чуть другими флагами.
- **Кнопка в Telegram — не защита.** `callback_data` видит любой, кому
  переслали сообщение, поэтому решение принимается только от
  `TELEGRAM_ADMIN_CHAT_ID`; пустое значение = не разрешено никому.
  В `callback_data` едет версия, а не список id: лимит Telegram — 64 байта,
  и трёх UUID туда уже не влезет. Заодно это правильная семантика — человека
  спросили про релиз, а не про список строк.
- **Две доставки, обе со своей отметкой** (`notified_at`, `reported_at`):
  вопрос «можно?» и ответ «вот как прошло» теряются независимо, и человек,
  нажавший «обновить» и не услышавший ничего, не отличает медленное
  обновление от сломанного.

**Что не проверено:** сам `update_node.sh` на живой ноде — в этой среде нет
запущенного демона Docker. Разбор его вывода, все ветки решений, подавление
повторов и порядок установки покрыты тестами (`tests/test_xray_updates.py`,
`tests/test_api_xray_updates.py`, `bot/tests/test_updates.py`).
